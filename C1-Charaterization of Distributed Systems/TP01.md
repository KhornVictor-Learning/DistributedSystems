## Question 1: Server-to-Server Request Forwarding

### 📌 Problem Statement
> **"What happen if the request needs to be forwarded from a server to another server?"**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 1)*

---

### 📖 Lesson & Research Context
* **Slide 9 (`C01.pdf`)** defines the fundamentals of client-server interaction:
  * A **Server** is a running program (a process) that accepts requests from programs on other computers to perform a service and responds back.
  * The requesting process is the **Client**.
  * A **Remote Invocation** is the complete interaction from the time a client sends its request until it receives back the response.
* **Coulouris (Chapter 1, Section 1.4)** explains that servers themselves frequently need to access other services. In modern multi-tier architectures (e.g., 3-tier web applications, microservices, reverse proxies, and recursive DNS resolvers), servers do not always handle requests in isolation.

---

### 💡 Detailed Answer

When a client request must be forwarded from Server 1 to Server 2, the following technical processes and architectural effects occur:

```
+------------+       1. Client Request (Remote Invocation)       +--------------+
|   Client   | ------------------------------------------------> |   Server 1   |
|            |                                                   | (Web / Proxy)|
+------------+                                                   +--------------+
      ^                                                                 |
      |                                                                 | 2. Forwarded Request
      |                                                                 |    (Role Reversal:
      |                                                                 |     Server 1 becomes Client)
      |                                                                 v
      |       4. Final Assembled Reply                           +--------------+
      +--------------------------------------------------------- |   Server 2   |
                                 OR                              | (Backend DB/ |
      +--------------------------------------------------------- |  App Service)|
      |       3. Sub-result Reply to Server 1                    +--------------+
      v       (Server 1 passes it back to Client)
```

#### 1. Role Inversion (Server becomes a Client)
* As defined in Slide 9, a server normally processes requests and sends replies. However, when forwarding a request, **Server 1 temporarily assumes the role of a client**.
* Server 1 initiates a **secondary remote invocation** towards Server 2, sending a new request message and waiting for Server 2's response message before it can finish serving the original client.

#### 2. Increased Accumulated Latency (Turnaround Delay)
* The total turnaround time experienced by the end client increases because network transmission and processing delays compound:
  $$\text{Latency}_{\text{Total}} = \text{RTT}(\text{Client} \leftrightarrow \text{Server}_1) + \text{Processing}(\text{Server}_1) + \text{RTT}(\text{Server}_1 \leftrightarrow \text{Server}_2) + \text{Processing}(\text{Server}_2)$$
* Additional computational overhead is introduced for **marshaling (serialization)** and **unmarshaling (deserialization)** of data at each hop.

#### 3. Connection, State, and Correlation Tracking
* Server 1 must maintain state context (such as an open TCP socket descriptor, memory buffers, or a **Correlation ID / Session ID**) to remember which client request belongs to which pending response from Server 2.
* Server 1's worker threads or asynchronous event loops must remain allocated (or suspended) while waiting for Server 2.

#### 4. Handling Partial Failures and Independent Crashes
* As highlighted in **Slide 7 and Slide 15 (`C01.pdf`)**, failures in distributed systems are **partial and independent**:
  * If Server 2 crashes, is overloaded, or the network link between Server 1 and Server 2 fails, Server 1 cannot immediately tell whether Server 2 died or is simply slow.
  * Server 1 must enforce **timeouts** and **failure masking / toleration** techniques (Slide 15):
    * Retry the operation (if idempotent),
    * Failover to a redundant replica of Server 2, or
    * Return a meaningful error to the client (e.g., `HTTP 502 Bad Gateway` or `HTTP 504 Gateway Timeout`) rather than leaving the client hanging.

#### 5. Security & Credential Delegation
* In according with **Slide 13 (`C01.pdf`)** on security (confidentiality and integrity), Server 1 must securely propagate the client's identity or authorization claims (e.g., OAuth tokens, JWTs, mutual TLS) to Server 2 so Server 2 can verify access permissions.

#### 6. Protocol & Data Format Transformation (Heterogeneity Masking)
* As noted in **Slide 10 & 11 (`C01.pdf`)**, distributed systems face heterogeneity across networks, OS, and hardware. Server 1 often acts as a gateway translating client protocols (e.g., `HTTP/REST/JSON`) into backend protocols used by Server 2 (e.g., `gRPC/Protocol Buffers` or binary SQL wire protocols).

---

### 🌟 Concrete Example
* **E-Commerce Web Application**:
  1. A user clicks "Checkout" in a web browser (Client).
  2. The Web/API Server (Server 1) receives the HTTP POST request.
  3. Server 1 cannot complete payment alone; it forwards the transaction details via a secure API request to an internal Payment Gateway Server or Bank Server (Server 2).
  4. Server 1 waits for Server 2 to approve the charge, records the transaction in its local database, and returns a confirmation response to the browser.

## Question 2: Peer-to-Peer Computing & Example

### 📌 Problem Statement
> **"What is peer-to-peer computing, give an example?"**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 2)*

---

### 📖 Lesson & Research Context
* **Slide 3 (`C01.pdf`)**: "Distributed systems mainly rely on resource sharing. Resource refer to things that can be shared in a networked computer system."
* **Slide 9 (`C01.pdf`)**: Explains the asymmetric Client-Server model where servers manage resources and clients only request them.
* **Coulouris (Chapter 1, Section 1.4)** contrasts the centralized Client-Server model with **Peer-to-Peer (P2P)** architecture:
  * In client-server, the server is a bottleneck and a single point of failure.
  * In peer-to-peer, all participating processes run similar programs and perform similar functions, sharing resources cooperatively without centralized coordination.

---

### 💡 Detailed Answer

#### 1. Definition of Peer-to-Peer (P2P) Computing
**Peer-to-Peer (P2P) computing** is a decentralized distributed architecture where all participating computers (known as **peers** or **nodes**) have **equivalent capabilities, privileges, and responsibilities (symmetric roles)**.

In contrast to the asymmetric Client-Server model:
* There is no dedicated central server controlling resources.
* Every peer operates simultaneously as both a **client** (requesting data/services) and a **server** (providing data/services to other peers). In distributed computing, such an entity is termed a **servant** (*server + client*).
* Nodes communicate and share hardware resources (processing power, disk storage, and network bandwidth) directly among themselves over the network.

```
       CLIENT-SERVER MODEL                               PEER-TO-PEER (P2P) MODEL
    (Asymmetric / Centralized)                         (Symmetric / Decentralized)

         Client       Client                                Peer A <---------> Peer B
             \         /                                      ^   \           /   ^
              v       v                                       |    \         /    |
          [ Central Server ]                                  |     \       /     |
              ^       ^                                       |      v     v      |
             /         \                                      v       \   /       v
         Client       Client                                Peer C <---------> Peer D
  • Server is bottleneck & SPOF                      • Every peer is Client AND Server
  • Clients only consume                             • Self-scaling & resilient
```

#### 2. Key Architectural Advantages of P2P Systems
1. **High Scalability (Self-Scaling)**: In client-server systems, adding more clients increases load on the central server until it bottlenecks. In P2P, every newly joined node adds both demand *and* resource capacity (bandwidth and storage) to the collective system.
2. **Resilience & Fault Tolerance**: In accordance with the principle of **independent failures** (Slide 7 & 15), if any individual peer disconnects or crashes, the network continues functioning because data and tasks are distributed across many alternative nodes.
3. **Cost Efficiency**: Eliminates the expense of purchasing and maintaining massive centralized server farms.

---

### 🌟 Concrete Example: The BitTorrent File Sharing Protocol
* **Overview**: **BitTorrent** is a widely deployed peer-to-peer file distribution protocol used for sharing large files (such as OS images, datasets, and software releases) efficiently across the Internet.
* **How It Operates**:
  1. A large file (e.g., a 4 GB Ubuntu Linux ISO) is split into thousands of small, fixed-size chunks (e.g., 512 KB or 1 MB each).
  2. When a user joins a torrent "swarm" to obtain the file:
     * **As a Client (Downloader)**: The user's computer concurrently requests and downloads different missing chunks from multiple other peers in the swarm.
     * **As a Server (Uploader / Seeder)**: As soon as the user's computer finishes downloading any chunk, it immediately makes that chunk available and uploads it to other peers that need it.
  3. Because the upload burden is distributed across thousands of peers rather than a single web server, download speeds increase as more users participate.

* **Other Prominent P2P Examples**:
  * **Blockchain Networks (e.g., Bitcoin, Ethereum)**: A decentralized public ledger where thousands of mining and validating nodes verify transactions and maintain consensus without a central bank.
  * **IPFS (InterPlanetary File System)**: A peer-to-peer hypermedia protocol where files are content-addressed and hosted collaboratively by participating nodes.

## Question 3: Client-Server Program between Web Browser and Web Server

### 📌 Problem Statement
> **"Explain client-server program between web browser and web server, give an EX"**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 3)*

---

### 📖 Lesson & Research Context
* **Slide 8 (`C01.pdf`)**: Introduces **Resource Sharing** and **Services**:
  * "A service is a part of computer system that manages a collection of related resources, and presents their functionality to users and applications."
* **Slide 9 (`C01.pdf`)**: Formally defines the **Client-Server Paradigm**:
  * **Server**: A running program (process) that accepts requests from programs on other computers to perform service and responds back.
  * **Client**: The requesting process.
  * **Remote Invocation**: A complete interaction from the time a client sends its request until it receives back the response.
* **Coulouris (Chapter 1, Section 1.2 & 1.4)**: The World Wide Web is the preeminent example of client-server distributed computing, operating via standard URL naming, HTTP protocol, and HTML presentation.

---

### 💡 Detailed Answer

#### 1. Concept and Roles
The interaction between a Web Browser and a Web Server represents the standard implementation of the **Client-Server Computing Model**:
* **Web Browser (The Client)**: An interactive application (e.g., Google Chrome, Mozilla Firefox) executing on the user's local computer. It issues requests for resources, parses received data, and renders content to the screen.
* **Web Server (The Server)**: A long-running service daemon (e.g., Apache HTTP Server, Nginx) hosted on a remote networked computer. It listens continuously on a designated transport port (port 80 for HTTP, port 443 for HTTPS), manages web documents (HTML, CSS, JS, images, databases), processes client requests, and replies with appropriate data.

```
+--------------------+                                         +--------------------+
|    Web Browser     |                                         |     Web Server     |
|   (Client Node)    |                                         |   (Server Host)    |
+--------------------+                                         +--------------------+
          |                                                               |
          | 1. DNS Resolution (Translates Hostname to IP)                 |
          | ------------------------------------------------------------> |
          |                                                               |
          | 2. TCP 3-Way Handshake (SYN -> SYN-ACK -> ACK on Port 80/443) |
          | <===========================================================> |
          |                                                               |
          | 3. Remote Invocation: HTTP Request (GET /index.html)          |
          | ------------------------------------------------------------> |
          |                                                               | [Web Server executes:
          |                                                               |  - parses request
          |                                                               |  - verifies security
          |                                                               |  - reads file/database]
          |                                                               |
          | 4. Remote Invocation: HTTP Reply (200 OK + HTML Payload)      |
          | <------------------------------------------------------------ |
          |                                                               |
          v                                                               v
  [Browser parses HTML,
   fetches linked assets,
   and renders the page]
```

#### 2. The Complete Remote Invocation Lifecycle
1. **User Request & URL Specification**: The user enters a URL into the browser (e.g., `http://www.itc.edu.kh/index.html`).
2. **Domain Name Resolution (DNS)**: Because the Internet uses IP routing (Slide 10), the browser contacts a DNS server to resolve `www.itc.edu.kh` into an IP address (e.g., `119.82.252.38`).
3. **Connection Establishment (TCP Handshake)**: The browser opens a reliable TCP socket connection to port 80 of the resolved IP address.
4. **Sending Request Message (Client Invocation)**: The browser formats and sends an HTTP Request message containing the HTTP method (`GET`), the target path (`/index.html`), protocol version, and request headers.
5. **Server-Side Processing**: The web server process:
   * Accepts the incoming socket connection.
   * Parses the request string.
   * Maps the resource path `/index.html` to a physical file on disk or invokes a script (e.g., PHP/NodeJS).
   * Packages the result into an HTTP Response message.
6. **Sending Reply Message (Server Response)**: The server transmits the response message containing an HTTP status code (`200 OK`), headers (`Content-Type: text/html`), and the requested HTML document body over the TCP socket.
7. **Client Rendering & Secondary Invocations**: The browser receives the response, parses the HTML, builds the Document Object Model (DOM), and triggers subsequent client-server invocations for any linked resources (stylesheets, images, scripts).

## Question 4: The 2 Alternative Ways for Byte Ordering of Integers

### 📌 Problem Statement
> **"Explain the 2 alternative ways for byte ordering of integers."**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 4)*

---

### 📖 Lesson & Research Context
* **Slide 10 (`C01.pdf`)** highlights the challenge of **Heterogeneity**:
  * "Computer hardware: data types such as integers may be represented in different ways on different kinds of hardware."
* **Slide 11 (`C01.pdf`)** introduces **Middleware**:
  * "Middleware is a software layer that provides a programming abstraction, and hides the heterogeneity of underlying networks, hardware, OS and programming languages..."
* **Coulouris (Chapter 1, Section 1.5.1 & Chapter 4)** explains data representation:
  * Integers (16-bit, 32-bit, 64-bit) are stored across multiple byte addresses. Different CPU hardware architectures store multi-byte integers in different byte orders. This hardware heterogeneity is called **Endianness**.

---

### 💡 Detailed Answer

#### 1. Why Byte Ordering Matters
Computer memory is byte-addressable (each address holds exactly 8 bits = 1 byte). However, integers generally require multiple bytes:
* A **16-bit integer (short)** requires **2 bytes**.
* A **32-bit integer (long / standard int)** requires **4 bytes**.
* A **64-bit integer** requires **8 bytes**.

When storing a multi-byte integer in consecutive memory addresses, a processor architecture must decide: *Which byte is placed at the lowest (first) memory address?*  
This yields two alternative conventions: **Big-Endian** and **Little-Endian**.

---

#### 2. The Two Alternative Ways

| Dimension | 1. Big-Endian | 2. Little-Endian |
| :--- | :--- | :--- |
| **Fundamental Rule** | The **Most Significant Byte (MSB)** is stored at the **lowest memory address** (the first byte). | The **Least Significant Byte (LSB)** is stored at the **lowest memory address** (the first byte). |
| **Sequential Order** | Bytes progress from highest-order to lowest-order ($MSB \to LSB$). | Bytes progress from lowest-order to highest-order ($LSB \to MSB$). |
| **Intuition / Analogy** | Matches natural human reading order for Western numbers (writing thousands first, then hundreds, tens, and units). | Stores the lowest units first, followed by tens, hundreds, and thousands. |
| **Hardware Architectures** | IBM z/Architecture mainframes, Motorola 68000, Sun SPARC, PowerPC. | Intel x86, AMD64 (x86-64), modern ARM processors (running in default little-endian mode). |
| **Networking Standard** | **Yes**: Standardized as the official **Network Byte Order** across TCP/IP. | No (Standard Host Byte Order for consumer PCs). |

---

#### 3. Concrete Demonstration with a 32-Bit Hexadecimal Integer
Consider the 32-bit integer:
$$\mathbf{0x12345678}$$

* **Breakdown into individual bytes**:
  * $\text{Byte 3 (Most Significant Byte - MSB)} = \mathbf{0x12}$
  * $\text{Byte 2} = \mathbf{0x34}$
  * $\text{Byte 1} = \mathbf{0x56}$
  * $\text{Byte 0 (Least Significant Byte - LSB)} = \mathbf{0x78}$

Suppose this integer is stored starting at memory address `0x1000`:

```
Memory Address:        0x1000      0x1001      0x1002      0x1003
                      +-----------+-----------+-----------+-----------+
Big-Endian (MSB 1st): |   0x12    |   0x34    |   0x56    |   0x78    |
                      +-----------+-----------+-----------+-----------+
                       ^ MSB (highest value byte at lowest address)
                       Transmitted on network as: 12  34  56  78

                      +-----------+-----------+-----------+-----------+
Little-Endian (LSB):  |   0x78    |   0x56    |   0x34    |   0x12    |
                      +-----------+-----------+-----------+-----------+
                       ^ LSB (lowest value byte at lowest address)
                       Stored in Intel x86 RAM as: 78  56  34  12
```

---

#### 4. The Heterogeneity Problem in Distributed Systems
* **The Problem**: If an Intel x86 laptop (Little-Endian) sends `0x12345678` over a network socket as raw memory bytes `[0x78, 0x56, 0x34, 0x12]`, and a Big-Endian computer reads those bytes in sequence, it interprets the number as:
  $$0x78563412 = \mathbf{2,018,915,346} \quad (\text{instead of } \mathbf{305,419,896})$$
* **The Solution (Middleware & Conversion Functions)**:
  * Internet protocols (IP, TCP, UDP) mandate **Big-Endian** as the universal **Network Byte Order**.
  * Distributed software uses conversion functions provided by standard libraries:
    * `htonl(uint32_t hostlong)`: Host to Network Long (converts 32-bit int to Big-Endian)
    * `htons(uint16_t hostshort)`: Host to Network Short (converts 16-bit int to Big-Endian)
    * `ntohl(uint32_t netlong)`: Network to Host Long (converts Big-Endian to local host order)
    * `ntohs(uint16_t netshort)`: Network to Host Short (converts Big-Endian to local host order)
  * Higher-level middleware (e.g., Sun XDR, CORBA CDR, Google Protocol Buffers, JSON) automates this serialization (marshaling) transparently.

## Question 5: Real-World Example of Each Transparency (8 Forms)

### 📌 Problem Statement
> **"Find 1 EX of each transparency"**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 5)*

---

### 📖 Lesson & Research Context
* **Slide 17 (`C01.pdf`)** formally defines **Transparency**:
  > *"Transparency is the concealment from the user and the application programmer of the separated components in a distributed system, so that the system is perceived as a whole rather than as a collection of independent components."*
* Slide 17 lists the **8 forms of transparency** established by the ISO Open Distributed Processing (ODP) reference model and Coulouris Chapter 1 (Section 1.5.7).

---

### 💡 Detailed Answer & Concrete Real-World Examples

```
+------------------------------------------------------------------------------------------------------+
|                                    THE 8 FORMS OF TRANSPARENCY                                       |
+---------------------+---------------------+---------------------+------------------------------------+
| 1. Access           | 2. Location         | 3. Concurrency      | 4. Replication                     |
| 5. Failure          | 6. Mobility         | 7. Performance      | 8. Scaling                         |
+---------------------+---------------------+---------------------+------------------------------------+
```

| # | Transparency Form | Formal Definition (`C01.pdf`, Slide 17) | Concrete Real-World Engineering Example |
| :-: | :--- | :--- | :--- |
| **1** | **Access Transparency** | Enables **local** and **remote resources** to be accessed using **identical operations**. | **Network File System (NFS) / POSIX System Calls**: A programmer uses standard file API calls (`open()`, `read()`, `write()`, `close()`) and commands (`cat`, `ls`) identically, whether the target file resides on the local NVMe drive or on a remote file server mounted over the network via NFS. |
| **2** | **Location Transparency** | Enables resources to be accessed **without knowledge of their physical or network location**. | **Uniform Resource Locators (URLs) & DNS**: When navigating to `https://www.google.com` or downloading an object from `https://s3.amazonaws.com/mybucket/file.pdf`, the user does not know which physical machine, server rack, datacenter, city, or numerical IP address physically stores the data. |
| **3** | **Concurrency Transparency** | Enables several **processes to operate concurrently** using **shared resources without interference** between them. | **Online Banking & ATM Database Transactions**: When two account holders simultaneously withdraw cash from a joint bank account, relational database systems (e.g., PostgreSQL, Oracle) utilize **ACID transaction locking** to ensure neither transaction overwrites the other or corrupts the shared balance. |
| **4** | **Replication Transparency** | Enables **multiple instances of resources** to be used to increase reliability and performance **without knowledge of the replicas** by users or programmers. | **Content Delivery Networks (CDNs, e.g., Cloudflare, Akamai)**: A user requests an image from a website. The CDN transparently serves the file from one of thousands of identical edge server replicas worldwide. The user and browser see only one unified URL and remain unaware of how many copies exist or which replica served them. |
| **5** | **Failure Transparency** | Enables the **concealment of faults**, allowing users and application programs to **complete their tasks despite the failure** of hardware or software components. | **High-Availability Reverse Proxy (e.g., HAProxy) & TCP Retransmission**: In a web farm, if a backend application server crashes while processing traffic, the reverse proxy detects the failure via health checks and automatically reroutes the request to a standby healthy node, so the end user never sees an error. |
| **6** | **Mobility Transparency** | Allows the **movement of resources and clients** within a system without affecting the **operation** of users or programs. | **Cellular Handover (GSM / 4G LTE / 5G) & Mobile IP**: A smartphone user conducting a live video call or downloading a file inside a moving car switches connection seamlessly from one cellular tower to another (or from home Wi-Fi to cellular data) without dropping the call or severing the active TCP connection. |
| **7** | **Performance Transparency** | Allows the system to be **reconfigured to improve performance as loads vary**. | **Cloud Auto-Scaling (e.g., AWS EC2 Auto Scaling / Kubernetes HPA)**: When an e-commerce website experiences an unexpected traffic surge during a flash sale, the infrastructure dynamically spins up additional container pods/virtual machines and re-balances load, preserving response latency without modifying application code. |
| **8** | **Scaling Transparency** | Allows the system and applications to **expand in scale** without making changes to the **system structure** or the **application algorithms**. | **The Domain Name System (DNS)**: The global DNS began in the 1980s with thousands of hosts and has expanded to billions of devices and domains today. Its hierarchical, delegated tree structure and distributed caching allow continuous massive growth without rewriting client DNS lookup software. |

## Question 6: Functional and Nonfunctional Properties of a System with Examples (QoS)

### 📌 Problem Statement
> **"Find functional and nonfunctional properties of a system with EX (QoS)"**  
> *(Source: `C01.pdf`, Page 19 / TP1 Question 6)*

---

### 📖 Lesson & Research Context
* **Slide 6 (`C01.pdf`)**: Lists **Quality of Service (QoS)** as one of the 8 fundamental challenges of distributed systems.
* **Slide 18 (`C01.pdf`)**: Dedicated slide on **Quality of Service**:
  > *"The main nonfunctional properties of systems that affect the QoS experienced by clients and users are reliability, security and performance. Performance in here refers to the ability to meet timeliness guarantees, EX: multimedia applications."*  
  > *"Adaptability to meet the changes of system configurations and resource availability is the most important aspect of QoS."*  
  > *"Normally, QoS refers to the ability of systems to meet such deadlines. It depends on the availability of the computing and network resources at the appropriate times."*
* **Coulouris (Chapter 1, Section 1.5.8)** distinguishes between:
  * **Functional requirements**: What the system does.
  * **Non-functional properties (QoS)**: The quality, performance, and operational constraints under which those services are delivered.

---

### 💡 Detailed Answer

```
                        SYSTEM SPECIFICATION PROPERTIES
                                       |
                +----------------------+----------------------+
                |                                             |
     [ FUNCTIONAL PROPERTIES ]                   [ NON-FUNCTIONAL PROPERTIES (QoS) ]
     "WHAT the system does"                      "HOW WELL the system performs"
     - Operations and services                   - Performance & Timeliness (Deadlines)
     - Business logic and functions              - Reliability & Availability
     - Input and output data flows               - Security
                                                 - Adaptability
```

---

### 1. Functional Properties

#### Definition
**Functional properties** define the **specific functions, operations, behaviors, and tasks** that a system must execute. They define **what** the system does in response to specific inputs and how it transforms data to satisfy user needs.

#### Concrete Examples
* **In an Online Banking System**:
  * The system allows an authenticated user to check their account balance.
  * The system allows a customer to transfer money to another account.
  * The system generates a downloadable monthly account statement in PDF.
* **In a Distributed Video Streaming System (e.g., YouTube / Netflix)**:
  * A user can search for a video title using keywords.
  * A user can click "Play" to start streaming a video.
  * A user can add a video to a custom playlist.

---

### 2. Non-Functional Properties (Quality of Service - QoS)

#### Definition
**Non-functional properties** specify the **qualitative attributes, performance metrics, and operational constraints** governing the execution of functional properties. They define **how well** the system does what it does.

According to **Slide 18 (`C01.pdf`)**, the primary nonfunctional properties that constitute **Quality of Service (QoS)** in distributed systems are:
1. **Performance & Timeliness (Meeting Deadlines)**
2. **Reliability & Availability**
3. **Security**
4. **Adaptability**

---

### 3. Detailed Breakdown of Non-Functional QoS Properties with Concrete Examples

#### A. Performance and Timeliness Guarantees (Deadlines)
* **Slide 18 Principle**: Performance in QoS specifically refers to the **ability to meet timeliness guarantees**. It depends on having computing and network resources available at the appropriate times.
* **Concrete Example (Distributed Multimedia / Video Conferencing)**:
  * In a real-time video conferencing application (e.g., **Zoom, Google Meet**), the non-functional QoS requirements mandate:
    * **End-to-End Latency**: Audio and video packets must arrive with latency $\mathbf{< 150 \text{ ms}}$ to avoid conversational lag.
    * **Jitter (Delay Variation)**: Must be kept $\mathbf{< 30 \text{ ms}}$ using jitter buffers to prevent audio distortion.
    * **Frame Rate & Throughput**: Video must sustain at least **30 frames per second (fps)** at a bit rate of $\mathbf{\ge 2.5 \text{ Mbps}}$ for 1080p Full HD.

#### B. Reliability and Availability
* **Slide 18 Principle**: Reliability is the probability that the system operates continuously without failure over a given time. Availability is the percentage of time the system is operational and ready to process requests.
* **Concrete Example (Core Financial / Payment Gateway)**:
  * For a global payment gateway (e.g., **Visa, Stripe, PayPal**):
    * **Availability SLA**: The service must guarantee **$99.999\%$ uptime** ("five nines"), permitting no more than **5.26 minutes** of unscheduled downtime across an entire year.
    * **Failover Time**: Automatic failover to a redundant secondary datacenter must complete within **$< 30 \text{ seconds}$** if the primary site crashes.

#### C. Security
* **Slide 13 & 18 Principle**: Security encompasses **Confidentiality** (protection against unauthorized disclosure), **Integrity** (protection against alteration or corruption), and **Availability** (protection against interference).
* **Concrete Example (Healthcare / Electronic Health Records System)**:
  * In a distributed hospital management system:
    * **Confidentiality**: All patient health data transmitted over the network must be encrypted end-to-end using **TLS 1.3 with AES-256-GCM**.
    * **Integrity**: Digital signatures (SHA-256 with RSA/ECDSA) must verify that medical prescriptions have not been tampered with in transit.
    * **Access Control**: Role-Based Access Control (RBAC) and Multi-Factor Authentication (MFA) must be enforced on every client request.

#### D. Adaptability
* **Slide 18 Principle**: *"Adaptability to meet the changes of system configurations and resource availability is the most important aspect of QoS."*
* **Concrete Example (Adaptive Bitrate Streaming - YouTube / Netflix)**:
  * When a mobile user streaming video enters an area with poor network reception (bandwidth drops from 20 Mbps to 1 Mbps), the streaming client and media server dynamically adapt using **Adaptive Bitrate Streaming (ABR via MPEG-DASH or HLS)**:
    * The system seamlessly steps down the video stream from 1080p to 480p on-the-fly, preventing playback stutter, freezing, and buffering pauses.

| Dimension | Functional Properties | Non-Functional Properties (QoS) |
| :--- | :--- | :--- |
| **Core Question** | **WHAT** does the system do? | **HOW WELL** does the system perform? |

| **Verification Method** | Functional testing (Pass/Fail: Did the feature work?). | Performance / Stress testing, SLA metrics (latency, uptime %, encryption strength). |
