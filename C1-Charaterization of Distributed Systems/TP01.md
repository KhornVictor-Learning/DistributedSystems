## Question 1: Server-to-Server Request Forwarding

### 📌 Question
**What happens if the request needs to be forwarded from a server to another server?**

### 💡 Answer & Explanation
In distributed computing architectures (such as multi-tier web applications, microservices, proxy servers, or RPC call chains), a server frequently cannot satisfy a client request completely on its own. When a request is forwarded from Server 1 to Server 2, several key mechanisms and implications occur:

```
[ Client ] 
    |
    | 1. Client Request (Remote Invocation)
    v
[ Server 1 (Front-end / Intermediary) ]
    | -- Role Switch: Server 1 becomes a Client
    | -- Context & State Tracking (Correlation ID)
    |
    | 2. Forwarded Request (Secondary Remote Invocation)
    v
[ Server 2 (Back-end / Database / Service) ]
    |
    | 3. Sub-result / Response
    v
[ Server 1 (Front-end / Intermediary) ]
    | -- Aggregation, Transformation & Formatting
    |
    | 4. Final Response
    v
[ Client ]
```

#### 1. Role Transition (Dual Role / Role Reversal)
* **Server 1 switches roles**: Towards the original client, Server 1 acts as a **server**. However, towards Server 2, Server 1 acts as a **client**.
* Server 1 initiates a **secondary remote invocation** (e.g., via RPC, gRPC, REST/HTTP, or a message broker) directed to Server 2.

#### 2. Latency and Communication Overhead
* Total turnaround latency experienced by the client increases.
* The total response time is the sum of:
  $$\text{Latency}_{\text{Total}} = \text{Latency}_{\text{Client} \to \text{Server}_1} + \text{Processing}_{\text{Server}_1} + \text{Latency}_{\text{Server}_1 \to \text{Server}_2} + \text{Processing}_{\text{Server}_2} + \text{Return Network Latencies}$$
* Additional serialization (marshaling) and deserialization (unmarshaling) overhead is incurred at both hops.

#### 3. State and Correlation Management
* Server 1 must maintain an active connection context or tracking token (e.g., a **Correlation ID** or **Session ID**) to map Server 2's eventual response back to the pending client socket connection.
* Server 1 must manage internal resources (threads, memory buffers, open socket descriptors) while blocking or awaiting an asynchronous callback from Server 2.

#### 4. Handling Partial Failures and Timeouts
* In distributed systems, failures are **independent and partial**. If Server 2 crashes, becomes unreachable, or experiences heavy load:
  * Server 1 cannot immediately determine whether Server 2 crashed, is slow, or the network link failed.
  * Server 1 must implement **timeouts**, **retries**, or **circuit breakers**.
  * If Server 2 fails to reply, Server 1 must catch the timeout and return an appropriate status code to the client (such as `HTTP 502 Bad Gateway` or `HTTP 504 Gateway Timeout`) rather than hanging indefinitely.

#### 5. Security and Credential Delegation
* The client's identity, authentication tokens (e.g., OAuth 2.0 Bearer tokens, JWTs), and authorization claims must either be securely forwarded (delegated) to Server 2, or Server 1 must authenticate itself using a service account or mutual TLS (mTLS).

#### 6. Protocol and Data Translation
* Server 1 often serves as an **API Gateway** or protocol converter:
  * *Example*: Converting incoming public `HTTP/JSON` from the client into internal `gRPC/Protocol Buffers` or binary database protocols (e.g., PostgreSQL wire protocol) to communicate with Server 2.

## Question 2: Peer-to-Peer Computing & Example

### 📌 Question
**What is peer-to-peer computing, give an example?**

### 💡 Answer & Explanation

#### 1. Definition
**Peer-to-Peer (P2P) computing** is a decentralized distributed architecture where all participating computers (called **peers** or **nodes**) share equivalent capabilities, responsibilities, and privileges. 

Unlike the traditional **Client-Server model**—where roles are strictly asymmetric (clients only request, servers only respond)—P2P systems are **symmetric**:
* Every peer acts simultaneously as both a **client** (requesting resources or data) and a **server** (supplying resources or data to other peers). In distributed computing literature, such a dual-role node is often called a **servant**.
* Nodes coordinate and communicate directly with one another over the network without requiring a centralized coordinator or dedicated central server.

```
      [ Client-Server ]                             [ Peer-to-Peer (P2P) ]
    (Centralized / Asymmetric)                    (Decentralized / Symmetric)

       Client 1     Client 2                            Peer A <=======> Peer B
           \           /                                  ^   \         /   ^
            v         v                                   |    \       /    |
          [ Central Server ]                              |     \     /     |
            ^         ^                                   |      v   v      |
           /           \                                  v       \ /       v
       Client 3     Client 4                            Peer C <=======> Peer D
```

#### 2. Key Characteristics of P2P Systems
* **High Scalability**: As new peers join the network, they contribute additional storage, processing power, and upload bandwidth. The system's capacity grows dynamically with demand.
* **Absence of a Single Point of Failure (High Fault Tolerance)**: If any individual peer disconnects or fails, other peers continue operating and sharing data.
* **Decentralized Resource Sharing**: Direct sharing of storage space, computational cycles, and network bandwidth.

#### 3. Concrete Example: BitTorrent Protocol
* **Description**: **BitTorrent** is a popular peer-to-peer file distribution protocol used to transfer large data files across the Internet.
* **How it Works**:
  1. A large file (e.g., an Ubuntu Linux installation ISO) is split into hundreds of small equal-sized pieces (chunks, e.g., 256 KB or 1 MB each).
  2. When a user joins a torrent "swarm" to download the file, their computer contacts other peers holding pieces of that file.
  3. The peer acts as a **client** by downloading different chunks concurrently from multiple available peers.
  4. Simultaneously, the peer acts as a **server** (seeder/uploader) by uploading chunks that it has already received to other peers requesting them.
  5. Because upload and download burdens are distributed among thousands of peers, network bottlenecks are eliminated, and download speeds increase as more users participate.

* **Other Examples**:
  * **Blockchain Networks (e.g., Bitcoin, Ethereum)**: Every full node stores a copy of the distributed ledger and validates transactions cooperatively without a central bank.
  * **InterPlanetary File System (IPFS)**: A decentralized, peer-to-peer content-addressable storage protocol.

## Question 3: Client-Server Program between Web Browser and Web Server

### 📌 Question
**Explain client-server program between web browser and web server, give an EX**

### 💡 Answer & Explanation

#### 1. Concept of Client-Server Architecture
The **Client-Server model** is the foundational architecture of the World Wide Web. It divides distributed application tasks between two distinct communicating entities:
* **Client (Web Browser)**: The initiating process that runs locally on the user's computer or mobile device. Its primary responsibilities are accepting user input, issuing service requests, receiving responses, and formatting/rendering content for human interaction.
* **Server (Web Server)**: A long-running process (daemon) running on a remote host computer that continuously listens on a dedicated network port, manages web documents and media resources, processes incoming client requests, and sends back appropriate responses.

Communication between the web browser and web server takes place through a sequence called a **Remote Invocation**, utilizing the **HTTP (HyperText Transfer Protocol)** or **HTTPS (HTTP Secure)** operating over a reliable **TCP/IP** transport layer.

```
+--------------------+                                         +--------------------+
|    Web Browser     |                                         |     Web Server     |
|   (Client Node)    |                                         |   (Server Host)    |
+--------------------+                                         +--------------------+
          |                                                               |
          | -------- 1. DNS Lookup (Resolve Hostname to IP) ------------> |
          |                                                               |
          | -------- 2. Establish TCP Connection (3-Way Handshake) -----> |
          |                                                               |
          | -------- 3. Send HTTP Request Message (e.g., GET) ----------> |
          |                                                               | [Process Request,
          |                                                               |  Locate / Generate
          |                                                               |  Resource]
          | <------- 4. Return HTTP Response Message (Status + Data) ---- |
          |                                                               |
          | [Close or Keep-Alive TCP Socket]                              |
          v                                                               v
  [Parse & Render HTML]
```

#### 2. Step-by-Step Interaction Workflow
1. **User Action & URL Entry**: The user enters a Uniform Resource Locator (URL) into the browser address bar (e.g., `http://www.itc.edu.kh/index.html`).
2. **Domain Name Resolution (DNS)**: The browser queries a DNS server to translate the human-readable domain name `www.itc.edu.kh` into an IP address (e.g., `119.82.252.38`).
3. **TCP Socket Connection**: The browser opens a reliable TCP connection to the server's IP address on default port **80** (for HTTP) or port **443** (for HTTPS) via a 3-way handshake (`SYN` $\to$ `SYN-ACK` $\to$ `ACK`).
4. **Client Remote Invocation (HTTP Request)**: The browser constructs and transmits an ASCII/binary formatted HTTP request message specifying:
   * **Method**: `GET`, `POST`, `PUT`, `DELETE`, etc.
   * **Target Path**: Resource location (e.g., `/index.html`).
   * **Headers**: Metadata such as `Host`, `User-Agent`, `Accept`, `Accept-Encoding`.
5. **Server Processing**: The web server software (e.g., Apache HTTP Server, Nginx):
   * Parses the HTTP request.
   * Checks security permissions.
   * Fetches the requested file from local disk storage or invokes backend application code (PHP, Python, Java, Node.js).
6. **Server Response**: The server constructs and transmits an HTTP response message containing:
   * **Status Code**: `200 OK` (success), `404 Not Found`, `500 Internal Server Error`, etc.
   * **Headers**: `Content-Type` (e.g., `text/html`), `Content-Length`, `Set-Cookie`.
   * **Payload (Body)**: The actual HTML, CSS, JavaScript, or image data.
7. **Rendering**: The browser parses the returned HTML, constructs the Document Object Model (DOM), requests linked sub-resources (images, stylesheets, scripts), and renders the webpage visually on the user's screen.

#### 3. Concrete Example

* **Client Request Message**:
  ```http
  GET /index.html HTTP/1.1
  Host: www.itc.edu.kh
  User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) Chrome/120.0.0.0
  Accept: text/html,application/xhtml+xml
  Connection: keep-alive
  ```

* **Server Response Message**:
  ```http
  HTTP/1.1 200 OK
  Date: Fri, 16 Oct 2026 05:30:00 GMT
  Server: Apache/2.4.52 (Ubuntu)
  Content-Type: text/html; charset=UTF-8
  Content-Length: 324

  <!DOCTYPE html>
  <html lang="en">
  <head><title>ITC - Distributed Systems</title></head>
  <body>
    <h1>Welcome to Institute of Technology of Cambodia</h1>
    <p>Course: Characterization of Distributed Systems</p>
  </body>
  </html>
  ```

## Question 4: Two Alternative Ways for Byte Ordering of Integers

### 📌 Question
**Explain the 2 alternative ways for byte ordering of integers.**

### 💡 Answer & Explanation

#### 1. Concept of Endianness
In computer memory, storage is organized and addressed as a sequential array of individual bytes (8 bits each). However, standard integers are multi-byte data structures:
* A 16-bit integer occupies **2 bytes**.
* A 32-bit integer occupies **4 bytes**.
* A 64-bit integer occupies **8 bytes**.

Because an integer must span across several contiguous memory addresses, processor architectures choose between two alternative conventions for ordering these bytes in memory: **Big-Endian** and **Little-Endian**.

---

#### 2. The Two Alternative Ways

| Characteristic | Big-Endian | Little-Endian |
| :--- | :--- | :--- |
| **Storage Rule** | The **Most Significant Byte (MSB)** is placed at the **lowest (first) memory address**. | The **Least Significant Byte (LSB)** is placed at the **lowest (first) memory address**. |
| **Byte Progression** | Bytes proceed from highest significance to lowest significance (left-to-right). | Bytes proceed from lowest significance to highest significance (right-to-left). |
| **Human Analogy** | Corresponds to natural reading order of numbers (thousands $\to$ hundreds $\to$ tens $\to$ units). | Corresponds to writing units first, then tens, then hundreds. |
| **Typical Architectures** | IBM Mainframes (z/Architecture), Motorola 68k, SPARC, PowerPC. | Intel x86, AMD64 (x86-64), Apple Silicon (ARM64 in little-endian mode). |
| **Standard In Networking** | **Yes**: Standardized as **Network Byte Order** across the Internet (TCP/IP). | No (Host byte order for personal computers). |

---

#### 3. Concrete Memory Demonstration
Consider storing the 32-bit hexadecimal integer:
$$\mathbf{0x12345678}$$

* **Most Significant Byte (MSB)**: `0x12`
* **Intermediate Bytes**: `0x34`, `0x56`
* **Least Significant Byte (LSB)**: `0x78`

Suppose this integer is stored starting at base memory address `0x1000`:

```
Memory Address:        0x1000      0x1001      0x1002      0x1003
                      +-----------+-----------+-----------+-----------+
Big-Endian (MSB 1st): |   0x12    |   0x34    |   0x56    |   0x78    |
                      +-----------+-----------+-----------+-----------+
                       (MSB at 0x1000)                     (LSB at 0x1003)

                      +-----------+-----------+-----------+-----------+
Little-Endian (LSB):  |   0x78    |   0x56    |   0x34    |   0x12    |
                      +-----------+-----------+-----------+-----------+
                       (LSB at 0x1000)                     (MSB at 0x1003)
```

---

#### 4. Importance in Distributed Systems (Heterogeneity Challenge)
* If an Intel x86 workstation (Little-Endian) sends `0x12345678` over a network socket as raw bytes `[0x78, 0x56, 0x34, 0x12]`, and a Big-Endian mainframe reads them directly into memory, the mainframe will reconstruct the number as:
  $$0x78563412 = \mathbf{2,018,915,346} \quad (\text{instead of } \mathbf{305,419,896})$$
* **Solution**: To guarantee interoperability across heterogeneous hardware, network communication standardizes on **Network Byte Order (Big-Endian)**.
* Operating systems provide standard C/POSIX socket conversion functions:
  * `htonl()`: Host to Network Long (32-bit integer)
  * `htons()`: Host to Network Short (16-bit integer)
  * `ntohl()`: Network to Host Long (32-bit integer)
  * `ntohs()`: Network to Host Short (16-bit integer)

## Question 5: Real-World Example of Each Transparency

### 📌 Question
**Find 1 EX of each transparency**

### 💡 Answer & Explanation
**Transparency** in distributed systems is defined as the concealment from the user and application programmer of the separated components, so that the system is perceived as a single integrated whole rather than a collection of independent machines.

The ISO Open Distributed Processing (ODP) reference model and Coulouris textbook define **8 forms of transparency**:

```
+----------------------------------------------------------------------------------------------------+
|                                    8 FORMS OF TRANSPARENCY                                         |
+-------------------+--------------------+--------------------+--------------------------------------+
| 1. Access         | 2. Location        | 3. Concurrency     | 4. Replication                       |
| 5. Failure        | 6. Mobility        | 7. Performance     | 8. Scaling                           |
+-------------------+--------------------+--------------------+--------------------------------------+
```

| # | Transparency Type | Definition | Concrete Real-World Example |
| :-: | :--- | :--- | :--- |
| **1** | **Access Transparency** | Enables local and remote resources to be accessed using identical operations and APIs. | **Network File System (NFS)**: In UNIX/Linux, standard C library system calls like `open()`, `read()`, and `write()`, as well as CLI utilities like `cat` and `cp`, operate identically whether the file is stored on the local NVMe SSD or on an NFS file server mounted across the network. |
| **2** | **Location Transparency** | Enables resources to be accessed without knowledge of their physical location or network host address. | **Uniform Resource Locators (URLs) & DNS**: When a user browses `https://www.google.com` or accesses an Amazon S3 object `https://s3.amazonaws.com/bucket/doc.pdf`, they do not know what physical rack, server host, data center, city, or IP address hosts the content. |
| **3** | **Concurrency Transparency** | Enables several processes to operate concurrently using shared resources without mutual interference. | **Automated Teller Machines (ATMs) & Relational Databases (e.g., PostgreSQL/Oracle)**: If two account holders concurrently attempt to withdraw funds or book the last seat on a flight, database transactions and row locks ensure neither transaction corrupts the balance or causes an oversold condition. |
| **4** | **Replication Transparency** | Enables multiple instances of resources to be used to increase reliability and performance without knowledge of the replicas by users or programmers. | **Content Delivery Networks (CDNs, e.g., Cloudflare, Akamai)**: A user loading static assets from a CDN accesses a single domain name, while the network silently routes the request to one of thousands of geographically dispersed edge replica servers worldwide without the user or client code knowing which replica served the data. |
| **5** | **Failure Transparency** | Enables the concealment of faults, allowing users and applications to complete tasks despite hardware or software failures. | **Reverse Proxy Failover (e.g., HAProxy / Nginx) & TCP Retransmission**: When a web cluster server crashes midway through servicing traffic, the front-end load balancer detects the failure via health-checks and automatically retries the client's request on a healthy standby node without throwing an error to the user. |
| **6** | **Mobility (Migration) Transparency** | Allows the movement of resources and clients within a system without affecting the operation of users or programs. | **Cellular Handover (GSM / 4G LTE / 5G) & Mobile IP**: A smartphone user on an active VoIP voice call or video conference moves from their home Wi-Fi to a cell tower while driving, switching access networks without dropping the call or terminating the TCP/UDP connection. |
| **7** | **Performance Transparency** | Allows the system to be dynamically reconfigured to improve performance as workloads vary. | **Cloud Auto-Scaling Groups (e.g., AWS EC2 Auto Scaling / Kubernetes Horizontal Pod Autoscaler)**: When an e-commerce platform experiences a spike in traffic during a flash sale, the infrastructure automatically spins up additional worker containers and redistributes traffic, maintaining response times without manual code reconfiguration. |
| **8** | **Scaling Transparency** | Allows the system and applications to expand in scale (users, traffic, nodes) without modifying the system structure or application algorithms. | **Domain Name System (DNS)**: The global DNS began in the 1980s with thousands of hosts and now manages billions of devices across millions of domains using a hierarchical tree structure with distributed caching and delegation, without requiring redesign of client lookup algorithms. |

## Question 6: Functional vs. Non-Functional Properties with Quality of Service (QoS) Examples

### 📌 Question

**Find functional and nonfunctional properties of a system with EX (QoS)**

### 💡 Answer & Explanation

Distributed system specifications are categorized into two fundamental classes of requirements: **Functional Properties** and **Non-Functional Properties (Quality of Service - QoS)**.

```
                            DISTRIBUTED SYSTEM PROPERTIES
                                         |
                   +---------------------+---------------------+
                   |                                           |
        [ Functional Properties ]                  [ Non-Functional Properties (QoS) ]
        "WHAT the system does"                     "HOW WELL the system does it"
        - Operations & Services                   - Performance & Timeliness
        - Input/Output data flows                  - Reliability & Availability
        - Business logic & features                - Security & Data Integrity
                                                   - Adaptability & Elasticity
```

---

### 1. Functional Properties

#### Definition
**Functional properties** specify the **specific behaviors, actions, services, and functions** that a system must execute. They define *what* the system does in response to specific inputs and how it transforms data to satisfy user needs.

#### Examples
* **Online Banking System**:
  * An authenticated customer can check their current account balance.
  * A customer can transfer \$100 from checking to savings.
  * The system generates and downloads a monthly statement in PDF format.
* **Distributed File System (e.g., Google Drive, NFS)**:
  * Users can upload files, create directories, share access permissions with other email addresses, and delete stored files.

---

### 2. Non-Functional Properties (Quality of Service - QoS)

#### Definition
**Non-functional properties** specify the **qualitative constraints, operational attributes, and performance criteria** under which the functional services must be delivered. They define *how well* the system performs.

In distributed systems, the primary non-functional properties affecting the **Quality of Service (QoS)** experienced by clients and users are:
1. **Performance & Timeliness (Deadlines & Latency)**
2. **Reliability & Availability**
3. **Security**
4. **Adaptability**

---

### 3. Detailed Quality of Service (QoS) Dimensions & Concrete Examples

#### A. Performance and Timeliness Guarantees (Deadlines)
* **Explanation**: In distributed systems, performance refers to the ability to satisfy **timeliness guarantees** and meet hard or soft deadlines. It depends on computing power and network resources being allocated at the appropriate times.
* **Example (QoS in Real-Time Multimedia Streaming)**:
  * In a distributed video conferencing platform (e.g., **Zoom, Google Meet**), audio and video packets must be delivered with:
    * **End-to-End Latency**: $< 150 \text{ ms}$ (to avoid conversational lag).
    * **Jitter (delay variation)**: $< 30 \text{ ms}$ (to prevent choppy voice audio).
    * **Throughput**: Minimum bandwidth of $2.5 \text{ Mbps}$ for Full HD 1080p video stream.

#### B. Reliability and Availability
* **Explanation**: Availability is the proportion of time that a system is accessible and capable of processing client requests correctly. Reliability is the probability that the system operates without failure over a given continuous interval.
* **Example (QoS in Core Banking / Payment Gateways)**:
  * A payment processing gateway (e.g., **Visa, Stripe, PayPal**) must guarantee:
    * **Availability SLA**: $\mathbf{99.999\%}$ uptime ("five nines"), which permits no more than **5.26 minutes** of total unscheduled downtime per calendar year.
    * **Mean Time to Recovery (MTTR)**: Automatic failover to a backup datacenter within $< 30 \text{ seconds}$ if the primary datacenter loses power.

#### C. Security
* **Explanation**: Protecting the confidentiality, integrity, and availability of sensitive data transmitted across open, insecure networks.
* **Example (QoS in Healthcare Distributed Records)**:
  * An electronic medical record system must enforce:
    * **Confidentiality**: All data in transit must be encrypted using **TLS 1.3 with AES-256-GCM**.
    * **Integrity**: All patient prescriptions must be cryptographically signed with digital certificates to prevent unauthorized tampering.
    * **Access Control**: Role-based access control (RBAC) and Multi-Factor Authentication (MFA) must be verified on every remote request.

#### D. Adaptability
* **Explanation**: The ability of a distributed system to dynamically adjust its configuration and resource usage in response to changes in workload, network bandwidth fluctuations, or hardware availability.
* **Example (QoS in Adaptive Video Streaming - YouTube / Netflix)**:
  * When a mobile user's network connection drops from high-speed 5G to weak 3G, the video player utilizes **Adaptive Bitrate Streaming (ABR via MPEG-DASH or HLS)** to dynamically scale video resolution from 4K down to 720p or 480p on-the-fly, preventing video freezing and buffering delays.

---

### 4. Summary Comparison: Functional vs. Non-Functional Properties

| Dimension | Functional Properties | Non-Functional Properties (QoS) |
| :--- | :--- | :--- |
| **Focus** | **What** the system does. | **How well** the system does it. |
| **Primary Scope** | Specific features, use cases, inputs, and outputs. | System-wide qualities: Performance, Reliability, Security, Adaptability. |
| **Measurement** | Binary pass/fail (Does the feature work?). | Quantitative metrics (Latency, throughput, uptime %, error rate). |
| **Example Requirement** | "The user can transfer funds to another account." | "The transfer must complete within 500 ms with 99.999% reliability over an encrypted channel." |
